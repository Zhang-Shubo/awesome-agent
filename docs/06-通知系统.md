# 06 · 通知系统

> 通知是 agent 的**反向通道**:平时是你找 agent,出了事、出了货是 agent 找你。没有这条通道,agent 只能被动等你想起来看日志。

## 定位与原则

通知系统要解决的是「agent 如何主动找到人」:抓取失败、交易信号触发、定时任务出货、服务健康恶化——这些事发生时,你可能在任何地方,唯一确定的是手机在身边。

四条原则(沉淀自真实项目):

1. **通知永不阻塞主流程**:未配置凭证 → 静默 no-op;发送失败 → 记日志不抛错。通知是锦上添花,绝不能因为「通知发不出去」搞挂业务本身。
2. **两档语义**:`alert(msg)` fire-and-forget(不 await、不抛错,99% 场景用它);`await send(msg)` 仅在「必须确认送达」时用(如交易确认)。
3. **跨项目同一对凭证、同名环境变量**:所有项目共用 `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` 这一套名字,agent 在任何项目里都不用重新学,运维口径可互相拷贝。
4. **分级防轰炸**:告警(⚠️ 出事了,必达)与 FYI(日报、跑批完成)分开;同类告警做去重/限频,别让一个抖动的数据源半夜发 200 条——**狼来了三次,通知系统就死了**。

## 渠道选型

| 渠道 | 接入成本 | 适合 | 结论 |
|------|---------|------|------|
| **Telegram** | 低:@BotFather 建 bot 两分钟,一个 HTTP POST 就能发 | 个人告警 + 日报,富文本(HTML)、长消息分段 | ⭐ **默认首选**,多项目多年验证 |
| **Discord** | 最低:频道建一个 Webhook,连 bot 都不用 | 已长住 Discord 的人;想按项目分频道归档 | 次选,或与 TG 并存 |
| **ntfy / Bark** | 低:自托管或公共实例,POST 即推 | 只要「手机弹一下」的极简场景 | 备选,适合不想碰 IM 平台的人 |
| **WhatsApp** | 高:Meta Business Cloud API,需企业号 + 模板消息审核 + 24 小时会话窗口限制 | 家人/协作者只用 WhatsApp 的场景 | ❌ 个人 agent 不推荐,门槛与限制远超收益 |
| **邮件** | 中:SMTP 或 API 服务 | 周报等低频长文,不求即时 | 补充渠道,不做告警主力 |

选型逻辑:**通知走你本来就天天开的 App**。渠道酷不酷不重要,你看不看得到才重要。

## Telegram(默认实现)

接入三步:

1. 找 [@BotFather](https://t.me/BotFather) `/newbot` 拿 `TELEGRAM_BOT_TOKEN`;
2. 给 bot 发一条消息,然后 `curl https://api.telegram.org/bot<token>/getUpdates` 从回包里拿你的 `chat.id` → `TELEGRAM_CHAT_ID`;
3. 发送就是一个 POST:

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/sendMessage" \
  -H 'content-type: application/json' \
  -d "{\"chat_id\":\"$TELEGRAM_CHAT_ID\",\"text\":\"⚠️ 出事了\",\"parse_mode\":\"HTML\",\"disable_web_page_preview\":true}"
```

工程细节(都写进了 [templates/notify.mjs](../templates/notify.mjs)):

- `parse_mode=HTML` 下正文里的 `< > &` **必须转义**,否则整条 400;
- 单条上限 4096 字符 → **按行在 4000 处分段**,别在字符中间硬切;
- 3 次重试;**429 遵循回包里的 `retry_after` 退避**,不要固定间隔硬怼;
- 关闭网页预览(`disable_web_page_preview`),告警消息里带链接时不刷屏。

## Discord(最低成本渠道)

频道设置 → 整合 → Webhook,拿到 URL 就完事,无需建 bot:

```bash
curl -s "$DISCORD_WEBHOOK_URL" \
  -H 'content-type: application/json' \
  -d '{"content":"⚠️ 出事了"}'
```

- 单条上限 2000 字符(比 TG 短,同样按行分段);
- 富文本用 `embeds`(标题/颜色/字段),告警红、日报灰,一眼分级;
- 一个项目一个 webhook 指到一个频道,天然按项目归档。

## WhatsApp(为什么不)

Meta Business Cloud API 的三道门槛:要 Meta 企业账号与商用号码;**主动发消息只能用预先审核的模板**,自由文本仅限用户主动发起后的 24 小时会话窗口;号码有封禁风险。这套设计是给「企业给客户发通知」的,不是给「你的 agent 给你发告警」的。除非收件人只用 WhatsApp,否则别选;真要接,把它当作 `notify()` 的一个可插拔渠道实现,主力仍留 TG/Discord。

## 统一抽象:notify() 可插拔

一个 `notify.mjs` 覆盖所有渠道,**配置了哪个就发哪个**(可多渠道并发):

```
notify(text, {level})           # 检测 config.env 里配置了哪些渠道
  ├─ TELEGRAM_BOT_TOKEN + CHAT_ID → 发 TG
  ├─ DISCORD_WEBHOOK_URL          → 发 Discord
  └─ 都没配                        → 静默 no-op(绝不抛错)
```

约定:

- 消息**开头带 emoji 分级**:`🚨` 必须处理 / `⚠️` 需要知道 / `✅` FYI 完成 / `📊` 日报——在锁屏通知里一眼定级;
- 消息带**项目名前缀**(如 `[feed]`),多项目共用一个 chat 时能分清来源;
- 同类告警**限频**:相同 key 的告警 N 分钟内只发第一条,恢复时补一条 `✅ 已恢复`;
- 通知发送本身的失败**只记日志**,永不上抛。

## 与其它支柱的关系

- **调度**([05](05-agent-工程约定.md)):poller 失败达到阈值才告警(单次失败先容忍),恢复必须补报;
- **模型三级后端**:模型调用记账超预算 → 告警,这是订阅额度的看门狗;
- **部署**:`deploy.sh` 结尾健康自测失败 → 告警,部署翻车第一时间知道。
