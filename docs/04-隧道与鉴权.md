# 04 · 隧道与鉴权

> cloudflared + Cloudflare Access:任何机器(家里的 GPU 机、云上的 VPS)上的服务,一条隧道上公网,统一邮箱验证码鉴权。不开任何公网端口。

## 安全模型(一条铁律)

**所有自建服务只监听 `127.0.0.1`,对外一律 cloudflared 隧道 + Cloudflare Access。**

- 服务器防火墙上没有任何业务端口对公网开放;
- 代码侧配合:服务默认 `HOST=127.0.0.1`;写操作可加可选的 `WRITE_TOKEN`,不设 token 时依赖「服务不暴露公网 + Access 鉴权」兜底;
- 故意公开的 API(如行情接口)也走隧道,只是不套 Access、CORS 放开——公开与否是 Access 策略的事,不是端口的事。

## cloudflared 隧道

每台需要对外的机器跑一个 cloudflared 守护进程,ingress 把子域映射到本机端口:

```yaml
# /etc/cloudflared/config.yml
tunnel: <tunnel-id>
ingress:
  - hostname: api.example.com
    service: http://127.0.0.1:8801
  - hostname: tools.example.com
    service: http://127.0.0.1:8910
  - hostname: ssh.example.com      # SSH 也能走隧道,外网可达
    service: ssh://127.0.0.1:22
  - service: http_status:404
```

```bash
cloudflared tunnel route dns <tunnel> api.example.com   # 子域绑定一条命令
```

要点:

- **一机一隧道,一服务一子域**。新服务上线 = ingress 加两行 + `tunnel route dns` 一条命令。
- **SSH over tunnel**:把家用机的 SSH 挂上隧道,在外面也能 `ssh` 回家——agent 的远程 GPU 任务就靠它。
- 已知坑:家用宽带上行有限(实测可能只有几百 KB/s),隧道适合传文本/控制流,大文件先压缩,长任务用 `nohup + 轮询` 抗瞬断。

## Cloudflare Access 鉴权

- 一条 Access 策略覆盖所有私有子域:邮箱验证码登录,30 天会话;
- 对个人使用来说体验足够好:每台设备每月登一次;
- 公开服务(status: api)不套 Access,其余全套。

## 开发期:SSH 隧道

上 Access 之前、或纯本地开发时,用 SSH 端口转发访问远端服务:

```bash
ssh -N -L 9800:127.0.0.1:9800 <host>   # 本地 9800 → 远端 9800
```

约定固定的本地端口映射表(写进项目 CLAUDE.md),agent 每次都用同一套端口,文档和命令可以互相拷贝。

## 远程 GPU 任务范式(抗断链)

经隧道往家用 GPU 机派长任务(如 Whisper 转录)的可靠模式:

1. 远端用 `nohup` 起进程——隧道瞬断不杀任务;
2. 远端 `flock` 全局 GPU 互斥锁——多任务串行,不挤显存;
3. 本地轮询远端状态文件,约定 `DONE / ERROR / ALIVE / DEAD` 四态;
4. `trap` 清理:本地中断时连带清掉远端孤儿进程;
5. **永久失败用专属退出码**(如 3),调用方据此入黑名单不再重试——区分「这次失败」和「永远不会成功」。
